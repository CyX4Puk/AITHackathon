# CONTEXT_PACK

## 1. Проблема одной фразой
B2B-клиент банка проверяет потенциальных контрагентов по объёмным отчётам, тратит время на ручной просмотр каждой компании по отдельности и рискует пропустить важные сигналы; нужен ИИ-агент, который выделяет риски, отвечает на уточняющие вопросы строго по данным и ускоряет принятие решения по сделке.

**Чья это работа (AJTBD):**
- Ситуация: перед сделкой или началом сотрудничества нужно оценить несколько юридических лиц-контрагентов.
- Хочу: быстро понять, с кем безопасно работать, где есть красные флаги и что требует дополнительной проверки.
- Чтобы: снизить риск плохой сделки и не тратить много времени на чтение длинных отчётов по каждому контрагенту отдельно.

## 2. Как делают сейчас и цена боли
Сейчас пользователь получает отчёт по одному контрагенту за раз и самостоятельно изучает всё больше информации по мере расширения состава данных в отчёте.

Текущая ситуация:
- просмотр каждого отдельного отчёта по каждой компании;
- ручная интерпретация финансовых, юридических и справочных сигналов;
- самостоятельное формирование вывода о целесообразности взаимодействия.

Цена боли выражена качественно, а не количественно:
- растёт время на анализ;
- ухудшается удобство продукта при росте объёма данных;
- есть риск пропуска значимых факторов;
- страдает retention, потому что решение должно повысить ценность продукта и возвращаемость клиентов.

## 4. Данные и ограничения

### 4.1. Источник и формат данных

- Для MVP и демонстрации используется предоставленная CSV/JSON-выгрузка
  контрагентов. Она моделирует внутреннюю предагрегированную базу данных банка.

- Реальный продукт получает данные из совокупности источников:
  СПАРК, закрытые коннекторы к государственным сервисам и внутренние
  банковские данные. В частности, часть риск-индикаторов может учитывать
  транзакционные данные банка.

- У команды нет доступа к внутренним API, банковскому контуру, закрытым
  коннекторам и реальной продовой базе. В демо нельзя рассчитывать на
  онлайн-запросы к источникам банка.

- Веб-поиск по открытым источникам допустим как дополнительная функция,
  например для поиска публичных расхождений между данными отчёта и сайтом
  компании. Он не является обязательной частью MVP.

- При противоречии между результатом веб-поиска и данными предоставленного
  отчёта приоритет имеют данные отчёта / банка. Агент не должен подменять
  ими банковские сведения без явного указания на расхождение.

### 4.2. Правила интерпретации данных

- `risk_level` является готовым банковским сигналом и принимается как
  корректный входной факт. Команда не обучает модель риска и не пытается
  восстановить закрытую формулу его расчёта.

- Ценность агента состоит не в дублировании `risk_level`, а в формировании
  объяснимого вывода на основе совокупности доступных фактов:
  риск-метки, финансовых данных, юридических сигналов и отсутствующих данных.

- Любой значимый вывод агента должен быть обоснованным: пользователь должен
  видеть конкретные факты, поля или значения отчёта, на которых построена
  рекомендация.

- Агент не должен выдумывать данные, приписывать компании несуществующие
  факты или делать выводы, не следующие из доступной информации.

- Если данных по критерию нет, агент обязан явно сообщать:
  «недостаточно данных для оценки данного критерия».
  Отсутствие сведений не должно интерпретироваться как отсутствие риска.

- Агент не должен выносить безусловный вердикт вида
  «нельзя взаимодействовать с контрагентом». Допустимый формат —
  рекомендация с объяснением: например, «рекомендуется
  дополнительная проверка», «обратите внимание на ...» или
  «целесообразно запросить дополнительные документы».

Не каталог и не скоринг, а объяснимый ИИ-анализ поверх данных конкретного банка с обоснованными ответами со ссылкой на поля отчёта и интерпретацией готовой риск-метки, а не cобственной моделью риска.


## 6. Гипотезы
1. Если пользователь первым экраном получает краткий risk summary с ключевыми фактами, то время до первого решения сократится, потому что ему не придётся читать весь отчёт линейно.
2. Если агент будет отвечать только по извлечённым фактам и сопровождать ответы ссылкой на источник внутри профиля компании, то доверие к решению будет выше.
3. Если добавить классификацию сигналов по уровням критичности, пользователь будет быстрее понимать, какие кейсы требуют ручной проверки.
4. Если поддержать вопросы естественным языком, то пользователю будет проще докопаться до причин риска без изучения всех разделов отчёта.
5. Если показать нескольких контрагентов рядом по одинаковому набору критериев, то пользователь быстрее выберет, с кем работать в первую очередь, и назовёт конкретные факты различия, потому что расхождения видны в одном месте, а не в трёх отчётах подряд. Критерии для сопоставления: банковская метка risk_level, ключевые финансовые показатели, юридические события, полнота данных.
6. Если по итогам сравнения агент выдаёт не ранжирование «лучше/хуже», а перечень различий с рекомендацией, что проверить по каждому кандидату, то пользователь примет это как обоснование собственного выбора, а не как чужой вердикт за него.
7. Если в интерфейс добавить виджеты с финансовой динамикой и ключевыми юридическими событиями, восприятие сложных данных станет проще. При отсутствии финотчётов виджет обязан явно показывать «нет данных», а не пустую визуализацию.


**Самое рискованное предположение (RAT):** пользователю действительно нужна не просто Q&A-обвязка вокруг отчёта, а готовая интерпретация риска, которой он будет доверять достаточно, чтобы принимать или ускорять бизнес-решение. Если доверия не будет, агент останется декоративным интерфейсом над тем же ручным процессом.


### План проверки RAT

- Подготовить 3–5 компаний с различными уровнями риска. Минимум одна компания — с неполными данными (нет финотчётности или пустые юридические разделы). Заранее определить факты, которые должны попасть в вывод по каждой.

- Задание А, одна компания. Показать пользователю или кейсодателю два варианта: исходный полный отчёт и прототип с risk summary, доказательствами и Q&A. Вопрос: «Можно ли рассматривать работу с этой компанией и что нужно проверить до сделки?»

- Задание Б, сравнение. Дать 3 компании в одной сессии, включая компанию с пропусками. Вопрос: «С кем из них вы начнёте работу и почему? Что проверите до сделки по каждому?»

- Зафиксировать метрики:
  время до первого обоснованного вывода, число открытых деталей и уточняющих вопросов, наличие ссылок на факты в ответе, субъективная оценка доверия.
  Дополнительно по заданию Б: сколько конкретных различий между компаниями пользователь назвал сам, как он поступил с компанией без данных, просил ли он «просто сказать, кто лучше» вместо перечня различий.

- Критерий успеха задания А:
  пользователь формирует корректный осторожный вывод быстрее, чем при просмотре полного отчёта, и может назвать минимум 2–3 факта, на которых основана рекомендация.

- Критерий успеха задания Б:
  пользователь называет приоритетного кандидата и минимум 2 конкретных различия из отчётов, при этом не трактует компанию с пропусками как безопасную.

## 9. Границы реализации MVP

### Ядро MVP — обязательно

- Поиск контрагента по ИНН в предоставленной CSV/JSON-выгрузке.
- Карточка контрагента: базовый профиль, банковская метка `risk_level`, ключевые финансовые показатели (динамика за 3 года из `finReports`), юридические события (проверки, исполнительные производства, арбитражи).
- Risk summary: краткий вывод с 3–5 значимыми фактами и явным указанием, какие критерии оценить невозможно из-за отсутствия данных.
- Grounded Q&A: ответы на уточняющие вопросы только по данным отчёта, со ссылками на конкретные поля.
- Рекомендация следующего шага без категоричного вердикта «не работать».
- Сравнение нескольких контрагентов (2–5) в одной сессии по единому набору критериев: `risk_level`, финансы, юридические события, полнота данных.
- Память в пределах сессии диалога.

### Второй эшелон — допустимые расширения, если успеем

- Контекст сделки: пользователь указывает планируемую сумму контракта, агент сопоставляет её с выручкой и прибылью контрагента за последний отчётный год и явно комментирует соразмерность (например, «сумма контракта превышает годовую выручку компании») без пересчёта собственной риск-метки. В таблице сравнения появляется строка «соразмерность сделки».
- Пресеты типовых вопросов пользователя для уточнения по отчёту.
- Веб-поиск по открытым источникам как дополнительная функция с явным отделением результатов от банковских данных.
- Отображение связанных компаний из блока `relatedCompanies`: список связей с реквизитами и пометкой, что риск-профиль связанной компании недоступен, если её нет в выгрузке.
- MCP-сервер как слой доступа агента к моковой базе.
- Экспорт результата: краткое резюме или сравнение в PDF/текст.

### Не входит в MVP хакатона

- Собственная модель риска или пересчёт `risk_level`.
- Поиск по отрасли, региону, названию (базовый вход — ИНН).
- Анализ рисков связанных компаний: в выгрузке есть реквизиты связей, но нет отчётов по самим связанным компаниям.
- Интеграция с внешними API источников данных (СПАРК, Rusprofile и др.) в рамках демо: базовая информация уже содержится в материалах кейса, обращение к платным сервисам конкурентов не предусмотрено условиями.
- Интеграция с банковскими системами и API.
- Большая база карточек контрагентов, каталог, долгосрочный мониторинг.
- Ролевая модель и разные интерфейсы для разных профессий.
- Долговременная память, избранное, история проверок.

### Roadmap — развитие после хакатона

- Контекст сделки: роли «поставщик/покупатель» и схема «предоплата/постоплата» как параметр, влияющий на интерпретацию рисков (риск неоплаты и риск недопоставки — разные наборы критериев).
- Интеграция с внешними источниками данных по API (СПАРК, государственные сервисы, открытые данные ЕГРЮЛ) для реального продукта: наполнение риск-профиля в реальном времени поверх архитектуры MVP. В рамках хакатона заменяется предоставленной CSV/JSON-выгрузкой.
- Проверка собственных данных по сделкам: договоры в приложении, контроль исполнения, рейтинг надёжности на основе истории выполнения обязательств — требует данных, которых нет в кейсе.
- Подбор поставщиков по видам деятельности и репутации поверх каталога компаний.
- Проверка собственников-физических лиц: ФССП, кредитная история — отдельный контур данных и согласования.
- Финансовые (кредитование, лизинг, факторинг) и юридические услуги как смежные банковские продукты, встраиваемые после проверки контрагента.
