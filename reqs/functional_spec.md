# Функциональное задание — MVP агента проверки контрагентов

**Статус:** рабочая версия к финальной сдаче 07.09.2026.
**Назначение:** единый документ, по которому (1) проектируется интерфейс, (2) ведётся разработка, (3) проверяется готовность приложения перед демо. Если пункт не описан здесь, он не входит в MVP.

**Источники:** постановка кейса (`requirements.md`), границы MVP и правила интерпретации (`context_pack.md` §4, §9), поля профиля и зоны отображения (`profile_fields.md`), правила сигналов, таблица «сигнал → шаг», сборка сводки и формат результата (`signal_rules.md` §1–6). При противоречии между этим документом и `signal_rules.md` в части условий срабатывания правил приоритет у `signal_rules.md`; в части поведения приложения и интерфейса — у этого документа.

---

## 1. Что делает приложение

Пользователь (предприниматель малого бизнеса, клиент банка) вводит ИНН одного или нескольких контрагентов. Приложение находит отчёты в моковой базе, прогоняет их через детерминированные правила и показывает:

- risk summary по каждому контрагенту: 4–5 фактов по фиксированной структуре и рекомендация следующего шага;
- карточку контрагента с полными данными отчёта по блокам;
- при 2–5 контрагентах — таблицу сравнения по единому набору строк и перечень различий;
- чат, в котором агент отвечает на уточняющие вопросы только по данным отчёта и ссылается на поля.

Приложение не пересчитывает метку риска банка, не ранжирует сигналы по важности, не выносит вердикт «работать / не работать» и не выдумывает данные.

## 2. Термины

| Термин | Значение |
|---|---|
| Отчёт | Один объект `GetFullReportResponse` из моковой базы; структура — `columns_spec.md` |
| Профиль | Срез отчёта по блокам A–G (`profile_fields.md`), подготовленный для карточки, сводки и сравнения |
| Сигнал | Сработавшее правило из `signal_rules.md` §3: `id`, `polarity`, `fields`, `message`, `zones` |
| Полярность | `negative` → `caution` → `gap` → `info` → `positive`; фиксированный порядок вывода внутри слота |
| Пробел (gap) | Раздел отчёта отсутствует; оценка по критерию невозможна. Не равен «не найдено» |
| Сводка (risk summary) | Заголовок (если есть) + 4–5 фактов по слотам `signal_rules.md` §5 + рекомендация |
| Сессия | Набор из 1–5 контрагентов и история диалога; живёт до перезагрузки страницы |
| Контекст сделки | Цель проверки и сумма контракта, задаваемые пользователем (второй эшелон) |

## 3. Данные

### 3.1. Источник

- **FR-D1.** Единственный источник данных в рантайме — `data/contractors_audit.snapshot.json` (100 отчётов, Mongo Extended JSON: `$date`, `$numberLong`). Внешних запросов за данными о компаниях приложение не делает.
- **FR-D2.** `reqs/contractors_audit.snapshot_C12613591.csv` — **другая выборка** из 100 компаний (пересечение по ИНН с JSON — 0 записей; распределение `riskLevel` в JSON: LOW 78 / MEDIUM 15 / HIGH 4 / UNKNOWN 3, в CSV: 85 / 11 / 1 / 3). Цифры срабатываний в `signal_rules.md` получены на CSV и служат проверкой логики правил, а не ожидаемым результатом на рантайм-данных. Все приёмочные тесты этого документа (§10) построены на JSON.
- **FR-D3.** Нормализация по `signal_rules.md` §1: `$date` → дата, `$numberLong` / строки-числа → число, `active` → boolean, пустые массивы и объекты без заполненных полей → раздел отсутствует, `finReports` сортируются по `common.year`. Кириллическая «а» в коде `аrbitrationDefendant` нормализуется.
- **FR-D4.** Признак ИП: `baseInfo.inn` из 12 знаков. Для ИП отсутствие `finReports`, `foundersInfo`, `taxSystem`, `companySize` — норма; тексты gap-правил меняются (`FIN_MISSING`), правила `FOUNDER_RECENT` и `AUTH_PERSON_RECENT` не применяются.

### 3.2. Движок правил

- **FR-D5.** Все правила `signal_rules.md` §3.1–3.5 реализованы детерминированно, без участия LLM. Результат по отчёту — объект формата `signal_rules.md` §6: `signals`, `gaps`, `summary_slots`, `next_steps`, плюс объект профиля для карточки.
- **FR-D6.** Одинаковый отчёт всегда даёт одинаковый результат (нет случайности, нет зависимости от времени, кроме `reportDate` из самого отчёта).
- **FR-D7.** Движок прогоняется на всех 100 отчётах JSON без исключений и падений; результат сохраняется как фикстура в репозитории (`data/fixtures/signals_100.json` или аналог) и используется в тестах. Ни у одной сводки не должно быть пустого слота 1–4.
- **FR-D8.** Дополнения к `signal_rules.md`, выявленные на JSON (внести в правила до финала):
  - `REG_BANKRUPTCY` и `status.reasonName`, содержащий «банкрот», дают **заголовок** сводки «Организация в процедуре банкротства ({date})», как `STATUS_CLOSED` и `STATUS_PENDING_EXCLUSION`; `STATUS_REASON` при этом не срабатывает. Кейс: 5032257375 (`reasonName` «признано несостоятельным (банкротом)…», код `liquidationStatus`).
  - Если `proceedsYears` пуст, а `profitYears` не пуст (выручка не указана ни за один год, прибыль есть), срабатывает gap «Выручка в отчётности за {y1}–{y2} не указана; масштаб и тренд оценить нельзя» (расширение `FIN_TREND_INSUFFICIENT`). Кейс: 9705152496.
  - `arbitrationByStatus`, у которого заполнены только пустые вложенные объекты, считается `notFound` → `ARB_NONE`.

## 4. Пользовательские сценарии и критерии приёмки

Приоритет P1 — обязательно к демо; P2 — обязательно, если ядро закрыто к вечеру 06.09; P3 — только при наличии времени, в проверку готовности не входит.

### US-1. Добавить контрагента по ИНН (P1)

Пользователь вводит ИНН в поле ввода или в чат; контрагент появляется в сессии, открывается его сводка.

Критерии приёмки:

1. **Given** пустая сессия, **When** ввод `9721159668` в поле ИНН и подтверждение, **Then** в панели сессии появляется «ООО "ТРАНСЛОРИУМ", ИНН 9721159668», открывается сводка; время до отображения детерминированной сводки ≤ 3 с.
2. **Given** пустая сессия, **When** сообщение в чат «проверь 9721159668», **Then** тот же результат, что в п. 1, плюс ответ агента со сводкой в чате.
3. **When** ввод ИНН, которого нет в базе (`0000000000`), **Then** сообщение «Отчёт по ИНН 0000000000 в базе не найден» и ссылка/кнопка «Показать доступные ИНН»; выдуманная карточка не появляется.
4. **When** ввод строки не из 10 или 12 цифр (`12345`, `ООО Ромашка`), **Then** сообщение «Введите ИНН: 10 цифр для юрлица или 12 для ИП»; поиск по названию не выполняется.
5. **When** повторный ввод ИНН, уже присутствующего в сессии, **Then** дубликат не создаётся, фокус переходит на существующего контрагента.
6. **Given** в сессии 5 контрагентов, **When** ввод шестого ИНН, **Then** сообщение «В сессии не больше 5 контрагентов. Удалите одного, чтобы добавить нового».
7. Пробелы и разделители внутри ИНН (`9721 159 668`) отбрасываются.

### US-2. Прочитать risk summary (P1)

Пользователь видит по контрагенту короткий вывод: заголовок (если есть), 4–5 фактов, список критериев, которые оценить нельзя, и рекомендацию следующего шага.

Критерии приёмки:

1. Состав и порядок фактов совпадают с `summary_slots` движка (`signal_rules.md` §5). Слоты 1–4 заполнены всегда; пятый факт — по правилу §5.
2. Каждый факт сопровождается полем-источником в формате `[поле]` (`[finReports[year=2025].liabilities.capitals]`). Коды `LOW`/`GREEN`/`CURRENT` пользователю не показываются, только подписи («низкий», «зелёный», «действует»).
3. Все сработавшие gap-правила выводятся отдельным блоком «Оценить нельзя» с формулировкой «недостаточно данных для оценки»; пустой блок допустим только если `gaps` пуст.
4. Рекомендация берётся из `signal_rules.md` §4 по `next_steps`; если `next_steps` пуст — строка «Стандартная проверка документов; сигналов, требующих отдельных действий, не выявлено». Формулировок «не работать», «отказаться», «однозначно надёжна» нет ни при каком наборе сигналов.
5. Сводка отображается **без ожидания LLM**: интерфейс сразу показывает `message` правил в порядке слотов; LLM-версия (сглаженный текст) подменяет её, когда готова. При недоступности LLM детерминированная сводка остаётся на экране, пользователь получает пометку «Текст сформирован по правилам без языковой модели».
6. Метки банка выводятся одной строкой без интерпретации «насколько это плохо»: «Оценка банка: риск высокий, ЗСК зелёный». `UNKNOWN` → «уровень риска не определён» и попадает в gaps.
7. Для HIGH-контрагента с чистыми фактами (592061218009: ИП, 1 год, ни одного негативного сигнала) сводка не объясняет метку фактами, которых нет, и не оспаривает её. Допустимая формулировка: «Метка банка высокая; факты отчёта её не раскрывают — модель риска банка учитывает данные, которых в отчёте нет».

### US-3. Открыть карточку контрагента (P1)

По клику на контрагента в панели сессии или на факт сводки пользователь открывает карточку с полными данными отчёта.

Критерии приёмки:

1. Карточка содержит блоки в порядке `profile_fields.md`: A «Оценка банка», B «Профиль», C «Финансы», D «Юридические события», E «Реестры ФНС», F «Дополнительно» (лицензии, госзакупки, учредители и руководитель, ОКВЭД, филиалы, налоговый режим). Заголовок карточки — краткое наименование, ИНН, ОГРН, статус, дата отчёта.
2. Блок C: таблица «год × (выручка, прибыль, капитал, краткосрочные обязательства, оборотные активы)» за годы из `finReports`, отсортированные по возрастанию; виджет динамики выручки и прибыли по годам. Если `finReports` нет — вместо таблицы и виджета текст «Финансовая отчётность в отчёте отсутствует» (для ИП — «ИП не публикует бухгалтерскую отчётность»), пустой график не рисуется. Год без выручки в виджете подписан «нет данных».
3. Блок D: исполнительные производства (активные отдельно от завершённых, с суммой или «сумма не указана»), сводка арбитража по ролям и статусам (`commonCount` как общее, роли — «из них»), список проверок со статусом. Пустой раздел подписан по типу: «не найдены» для `executionProceedings` / `arbitrationByStatus`, «сведений в отчёте нет» для `inspections`.
4. Блок E: негативные отметки с текстом банка полностью; позитивные — свёрнутый список «Проверено N реестров» с раскрытием.
5. Каждый сработавший сигнал отмечен в карточке рядом с породившим его полем (метка полярности). Коды-дубликаты `reputationalRisks` (`executionProceedings`, `arbitrationDefendant`, `profit`…) видны в блоке E как есть, но не дублируются в сводке.
6. Ссылка `[поле]` в сводке или в ответе чата при клике подсвечивает соответствующий блок карточки (P2; для P1 достаточно текстового отображения ссылки).
7. Все суммы — в рублях с масштабом (тыс. / млн / млрд ₽, 1 знак после запятой), даты — `дд.мм.гггг`, проценты — целые.

### US-4. Сравнить 2–5 контрагентов (P1)

Как только в сессии два и более контрагента, пользователь видит таблицу сравнения и перечень различий.

Критерии приёмки:

1. Таблица: колонки — контрагенты (краткое имя + ИНН), строки — по блоку G `profile_fields.md`: «Оценка банка», «Финансы», «Юридические события», «Реестры ФНС», «Полнота данных»; при заданной сумме сделки — «Соразмерность сделки» (P2). Ячейка — `message` сработавших правил с зоной `compare` в порядке полярностей; пустых ячеек нет (у каждой строки есть info/gap-fallback).
2. Ячейка «Полнота данных» перечисляет все `gaps` контрагента человеческим языком («нет финотчётности; нет сведений о проверках»); при пустом `gaps` — «Все разделы отчёта заполнены».
3. Под таблицей — «Различия»: список строк, в которых контрагенты отличаются по полярности или по наличию negative/caution-сигналов, с фактами по каждому. Одинаковые строки в различия не попадают.
4. Под различиями — «Что проверить до сделки»: по каждому контрагенту рекомендации из `signal_rules.md` §4.
5. Нет столбца «итог», «балл», «место», нет сортировки по «надёжности», нет цветовой шкалы «лучше / хуже» между контрагентами. Цвет допустим только для полярности сигнала внутри ячейки.
6. Удаление контрагента из сессии убирает его колонку; при одном оставшемся таблица скрывается, остаётся сводка.
7. Клик по имени контрагента в заголовке колонки открывает карточку.

### US-5. Задать уточняющий вопрос (P1)

Пользователь спрашивает в чате про контрагентов сессии; агент отвечает только по данным отчёта, со ссылками на поля.

Критерии приёмки:

1. Ответ на вопрос о факте отчёта («какая выручка у Транслориума за 2025?») содержит значение и ссылку: «806,3 млн ₽ [finReports[year=2025].common.proceeds]».
2. Ответ на вопрос о данных, которых в отчёте нет («сколько сотрудников?», «кто их клиенты?»), — «В доступных данных этой информации нет», без домыслов. Веб-поиск не выполняется (P1).
3. Вопрос о компании не из сессии («а что по 1660266560?») — агент добавляет контрагента в сессию через инструмент (с синхронизацией панели) и отвечает. Если ИНН не найден — п. 3 сценария US-1.
4. Вопрос «кто из них лучше / с кем работать?» — ответ перечисляет различия и рекомендации по каждому и заканчивается фразой вида «Решение за вами». Допустимо фактическое утверждение «у X по доступным данным нет негативных сигналов, у Y — два (активные исполнительные производства, открытые дела как ответчик)». Запрещены: «лучше», «надёжнее», «рекомендую работать с», числовой рейтинг, ранжированный список.
5. Вопрос «почему у компании высокий риск?» при отсутствии негативных фактов — ответ по п. 7 сценария US-2; агент не приписывает причины.
6. Каждое число, дата, название в ответе присутствует в данных отчёта или в результатах движка правил. Проверяется автоматически (FR-G3) и вручную на 20–30 вопросах (§9).
7. Ответ приходит ≤ 30 с при API-профиле LLM; при таймауте или ошибке — сообщение «Языковая модель недоступна; данные отчёта доступны в карточке», без зависания интерфейса.
8. Агент помнит контекст сессии: «а у второго?» после вопроса о выручке первого контрагента отвечает про второго контрагента сессии.

### US-6. Управлять сессией (P1)

1. Панель сессии показывает всех контрагентов (имя, ИНН, метка банка подписью), позволяет переключаться между ними, удалять по одному и очищать сессию целиком.
2. Очистка сессии сбрасывает и историю чата; агент не помнит контрагентов из предыдущей сессии.
3. Перезагрузка страницы = новая сессия; это допустимо и не считается ошибкой.

### US-7. Задать контекст сделки (P2)

1. Пользователь указывает цель проверки (варианты: «поставка», «госзакупка», «без контекста») и сумму контракта в рублях (необязательно).
2. При цели «госзакупка» в сводку допускаются `PROCUREMENT_WIN` / `PROCUREMENT_NONE` (слот 5), в карточке блок F «Госзакупки» поднимается выше.
3. При заданной сумме срабатывает `DEAL_AMOUNT_DISPROPORTION` (`signal_rules.md` §3.5), в таблице сравнения появляется строка «Соразмерность сделки». Метка банка не пересчитывается.
4. Контекст задаётся и через чат («планирую контракт на 50 млн»); агент подтверждает и обновляет сводки.

### US-8. Пресеты вопросов (P2)

Под полем чата — 5–6 кнопок с типовыми вопросами: «Почему такая оценка банка?», «Что с финансами?», «Есть ли долги и суды?», «Чего не хватает в отчёте?», «Что проверить до сделки?», при 2+ контрагентах — «В чём главные различия?». Нажатие отправляет вопрос в чат.

### US-9. Второй эшелон без гарантии (P3)

Связанные компании (`relatedCompanies`, только реквизиты, с пометкой «риск-профиль недоступен»); веб-поиск с явным разделением «данные банка / открытые источники»; экспорт сводки или сравнения в текст/PDF; MCP-сервер как транспорт к базе (архитектурно уже выбран, но для приёмки неважно, где живёт движок).

## 5. Ограничения на выводы агента (guardrails)

Проверяются на каждом ответе; нарушение любого пункта — блокер готовности.

| ID | Правило | Как проверяется |
|---|---|---|
| G1 | Метки `riskLevel`, `zskRiskLevel` не пересчитываются и не оспариваются | Поиск в ответах фраз «на самом деле риск», «метка завышена/занижена», собственных оценок «риск средний» при иной метке банка |
| G2 | Нет вердикта | Стоп-слова: «не работать», «не рекомендуем работать», «отказаться от сделки», «безопасна», «надёжна», «однозначно». Автопроверка регулярными выражениями + ручная |
| G3 | Каждое число / дата / название из ответа есть в данных | Автоматический валидатор: извлечь числа и `[поля]` из ответа, сверить с результатом инструмента; несовпадения логируются и показываются в режиме отладки |

## 6. Требования к интерфейсу

Документ задаёт состав экранов, элементы и состояния; визуальное решение (Gradio Blocks к 07.09) — на усмотрение разработчика при соблюдении пунктов ниже. Детальный проект интерфейса, соответствие компонентам Alfa Core Components и кликабельный макет — в `reqs/ui/` (`ui_design.md`, `mockup.html`).

### 6.1. Композиция

Один экран, три зоны:

- **Панель сессии** (слева или сверху): поле ввода ИНН + кнопка «Добавить»; список контрагентов сессии (имя, ИНН, метка банка подписью и цветом полярности `info`); удаление; «Очистить сессию»; кнопка «Доступные ИНН» (демо-помощник: список 100 ИНН с именами и метками). Второй эшелон: селектор цели и поле суммы сделки.
- **Рабочая область** (центр): вкладки «Сводка», «Карточка», «Сравнение» (последняя появляется при 2+ контрагентах и становится активной по умолчанию при добавлении второго).
- **Чат** (справа или снизу): история, поле ввода, пресеты (P2). Чат виден всегда, независимо от вкладки.

### 6.2. Состояния

| Состояние | Что показываем |
|---|---|
| Пустая сессия | Поле ИНН с плейсхолдером «ИНН: 10 цифр — юрлицо, 12 — ИП», подсказка «Добавьте 1–5 контрагентов», кнопка «Доступные ИНН», чат с приветствием агента в одну фразу |
| Загрузка отчёта | Индикатор на ≤ 3 с; интерфейс не блокируется |
| Сводка готова, LLM формирует текст | Детерминированная сводка + индикатор «уточняю формулировки»; после ответа LLM текст заменяется |
| LLM недоступна | Детерминированная сводка + пометка; чат сообщает об ошибке одним сообщением, поле ввода активно |
| ИНН не найден / невалиден / лимит | Сообщение рядом с полем ввода (см. US-1); состояние сессии не меняется |
| Один контрагент | Вкладки «Сводка», «Карточка»; вкладки «Сравнение» нет |
| 2–5 контрагентов | Добавляется «Сравнение» (таблица + различия + что проверить) |

### 6.3. Правила отображения

- Полярность сигнала передаётся цветом и пиктограммой: `negative` красный, `caution` оранжевый, `gap` серый с пунктиром, `info` нейтральный, `positive` зелёный. Цвет никогда не применяется к контрагенту целиком, только к сигналу.
- Метка банка выводится подписью («риск высокий») с цветом по её собственной шкале (LOW зелёный, MEDIUM жёлтый, HIGH красный, UNKNOWN серый), ЗСК — аналогично; это единственное место, где цвет отражает оценку, и оценка эта — банка.
- Ссылка `[поле]` — моноширинный текст приглушённого цвета; не ломает строку; при наведении — полный путь.
- Тексты банка из `reputationalRisks` (150–300 символов) — только в карточке, в сводке и сравнении — тексты правил.
- Виджет финансов: столбики по годам (выручка и прибыль), год без данных подписан «нет данных»; при отсутствии `finReports` виджет не рендерится.
- Длинные списки (исполнительные производства до 1744 записей у 5029069967, проверки до 100) — пагинация или свёртка «показать все N»; в карточке по умолчанию видны активные ИП и первые 10 завершённых.
- Ни один элемент интерфейса не показывает английские коды значений; допустимы только имена полей внутри `[…]`.

## 7. Контракт между компонентами

Для синхронной работы трёх участников фиксируются интерфейсы; транспорт (MCP / прямой вызов) на приёмку не влияет.

| Функция | Вход | Выход |
|---|---|---|
| `get_report(inn)` | ИНН строкой | Нормализованный `report` или `null` |
| `list_reports()` | — | Список `{inn, shortName, riskLevel}` по всем 100 отчётам (для «Доступные ИНН») |
| `analyze(inn, dealContext?)` | ИНН, опционально `{goal, amount}` | Объект `signal_rules.md` §6 + `profile` (блоки A–F) + `summary_text_deterministic` (строки `message` по слотам + рекомендация §4) |
| `compare(inns[], dealContext?)` | 2–5 ИНН | `{rows: [{criterion, cells: {inn: [signals]}}], differences: [...], next_steps: {inn: [...]}}` |
| `chat(session_id, message)` | Текст пользователя | Текст ответа + список использованных `[полей]` + результат валидатора G3/G4 |

Агент получает в контекст только результат `analyze` / `compare` и, по запросу, полный `report`; сырой отчёт не передаётся в промпт по умолчанию.

## 8. Нефункциональные требования

- **NFR-1.** Запуск одной командой (`docker compose up` или `make run`) с профилем LLM через переменную окружения; README описывает запуск на Mac без GPU (API-профиль).
- **NFR-2.** Движок правил на одном отчёте — ≤ 200 мс; на 100 отчётах — ≤ 10 с (используется для фикстуры и тестов).
- **NFR-3.** Детерминированная сводка на экране ≤ 3 с после ввода ИНН; ответ LLM ≤ 30 с; при превышении — состояние «LLM недоступна» из §6.2.
- **NFR-4.** Все вызовы инструментов и ответы LLM логируются с `session_id`, ИНН, длительностью и результатом валидаторов G2–G4, G9. Лог используется для отчёта о грандинге на защите.
- **NFR-5.** Тесты движка: юнит-тесты на каждое правило §3 с минимальными синтетическими отчётами + регрессионный тест «100 отчётов = фикстура». Тесты запускаются одной командой.
- **NFR-6.** Внешние сетевые вызовы — только к LLM API (если выбран API-профиль). Ни один компонент не обращается к сервисам проверки контрагентов.
- **NFR-7.** Язык интерфейса и ответов — русский.
