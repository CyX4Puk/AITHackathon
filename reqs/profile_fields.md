# Спецификация профиля контрагента

Источник данных: JSON-отчёт (`report` в выгрузке), структура `GetFullReportResponse` — см. `columns_spec.md`. Формат выгрузки — Mongo Extended JSON (`{"$date": …}`, `{"$numberLong": …}`); нормализация описана в `signal_rules.md` §1.

**Профиль** — не отдельная база, а подготовленный срез отчёта для карточки, сравнения, risk summary и контекста LLM. Полный JSON не передаётся в сводку целиком.

**Принципы**

- `baseInfo.riskLevel` и `zskRiskLevel` — готовые банковские метки; не пересчитываем и не оспариваем. Значение `UNKNOWN` (есть в выгрузке) выводим как «не определён», это пробел данных, а не «низкий риск».
- Универсального набора «главных» сигналов нет (подтверждено кейсодателем): значимость зависит от цели проверки. В ядре MVP — фиксированная структура блоков и фиксированный порядок полярностей внутри блока (риск-факты раньше нейтральных); субъективного ранжирования агентом нет.
- Правила срабатывания сигналов — в `signal_rules.md` (детерминированные IF/THEN). LLM формулирует текст и ссылается на поля; не выбирает «важные» поля сам.
- Факт ≠ пробел. Пустой массив («исполнительных производств не найдено») — факт. Пробел — когда раздела нет в отчёте. Пробел помечаем явно и не трактуем как отсутствие риска.
- Коды и английские значения (`LOW`, `GREEN`, `CURRENT`) пользователю не показываем, только русские подписи.

**Зоны отображения:** `summary` | `card` | `compare` | `qa` (чат / полный отчёт по запросу)

## Блок A — оценка банка (вход без пересчёта)

| Поле | Правило | summary | card | compare | qa |
|---|---|:---:|:---:|:---:|:---:|
| `baseInfo.riskLevel` | LOW / MEDIUM / HIGH → «низкий / средний / высокий»; UNKNOWN → «не определён» (gap) | ✓ | ✓ | ✓ | ✓ |

## Блок C — финансы

**Период:** последние 3 года с данными в `finReports` (сортировка по `finReports[].common.year`; в выгрузке массив не отсортирован). **Единицы:** рубли; в тексте — тыс. ₽ / млн ₽ с округлением до 1 знака.

| Поле / правило | Интерпретация | summary | card | compare | qa |
|---|---|:---:|:---:|:---:|:---:|
| `finReports[].common.proceeds`, `profit` | Выручка и прибыль по годам. `proceeds = 0` или `null` — нет данных за год; ключ `profit` часто отсутствует | ✓ | ✓ | ✓ | ✓ |
| Тренд выручки | Рост / падение / стагнация между первым и последним годом с ненулевой выручкой; при одном годе — «тренд оценить нельзя» | ✓* | ✓ | ✓ | ✓ |
| Тренд прибыли | Абсолютные значения, без процента; убыток за последний год — отдельный факт | ✓* | ✓ | ✓ | ✓ |
| `finReports[].liabilities.capitals` | Капиталы и резервы; отрицательный капитал — факт в сводке | ✓* | ✓ | ✓ | ✓ |
| `finReports[].liabilities.shortTermLiabilities.total` | Краткосрочные обязательства | — | ✓ | — | ✓ |
| `finReports[].liabilities.shortTermLiabilities.borrowedFunds` | Краткосрочные заёмные средства | — | ✓ | — | ✓ |
| `finReports[].liabilities.shortTermLiabilities.accountsPayable` | Кредиторская задолженность | — | ✓ | — | ✓ |
| `finReports[].assets.currentAssets.total` | Оборотные активы | — | ✓ | — | ✓ |
| Долговая нагрузка | `shortTermLiabilities.total > currentAssets.total` за последний год — факт «краткосрочные обязательства превышают оборотные активы» | ✓* | ✓ | ✓ | ✓ |
| `coefficient.sustainability`, `solvency`, `profitability` | Коэффициенты (есть у 19 из 100) | — | ✓ | — | ✓ |
| Полнота блока | Нет `finReports` (25 ИП + 8 юрлиц) или отчётность без выручки и прибыли (7) → «оценить финансы нельзя»; для ИП текст «ИП не публикует бухгалтерскую отчётность» | ✓ | ✓ | ✓ | ✓ |

## Блок E — реестры ФНС и репутационные факторы

Блок `reputationalRisks` — результат прогона по реестрам ФНС; заполнен у всех компаний (9–22 позитивных записи, до 6 негативных). Работаем по `code`, тексты банка (150–300 символов) — только в карточке.

| Поле | Правило | summary | card | compare | qa |
|---|---|:---:|:---:|:---:|:---:|
| `reputationalRisks.negative[]` — реестровые коды (`liquidationStatus`, `fnsBlocking`, `invalidAddress`, `invalidRegistrationData`, `invalidAuthpersonsData`, `dishonestProvider`, `disqualifiedAuthpersons`, `taxArrears`, `taxReporting`, `massAddress`, `massAuthpersons`) | Каждый — отдельный сигнал `REG_*`; в сводке одной строкой | ✓* | ✓ | ✓ | ✓ |
| `reputationalRisks.negative[]` — коды-дубликаты (`executionProceedings`, `arbitrationDefendant`, `profit`, `currentAssets` и др.) | Не выводим в сводку и сравнение: тот же факт даёт блок C/D. В карточке — как есть | — | ✓ | — | ✓ |
| `reputationalRisks.positive[]` | В сводке — одна строка «проверено N реестров, негативных отметок нет»; полный список — карточка | ✓* | ✓ | ✓ | ✓ |
| `massOkved` | Только карточка | — | ✓ | — | ✓ |
| Полнота блока | Блок отсутствует → пробел (в выгрузке — 0 компаний) | ✓ | ✓ | ✓ | ✓ |

## Risk summary — шаблон (ядро MVP)

Фиксированный порядок; в текст попадают до 5 фактов, не все сработавшие правила. Сборка — `signal_rules.md` §5.

0. Заголовок — «Организация не действует», только при CLOSED.
1. Оценка банка — `riskLevel` и `zskRiskLevel` одной строкой, без интерпретации «насколько плохо».
2. Финансы — тренд, убыток, отрицательный капитал, долговая нагрузка или «оценить финансы нельзя».
3. Юридические события — активные ИП, открытые дела как ответчик, нарушения по проверкам или «не найдены» / «сведений нет».
4. Реестры ФНС — негативные отметки одной строкой или «негативных отметок нет».
5. Пятый факт — второй негативный факт из блока D или C, иначе один факт из блока F (молодая компания, смена руководства, лицензия, соразмерность сделки).
6. Рекомендация следующего шага — по таблице `signal_rules.md` §4, без вердикта «не работать».

Слоты 1–4 заполнены всегда, поэтому сводка — 4 или 5 фактов. Остальные поля отчёта доступны в карточке и Q&A.

```
JSON report (Mongo Extended JSON)
  → нормализация типов (signal_rules.md §1)

  → применение правил из signal_rules.md §3
  → объект профиля + signals / gaps / summary_slots / next_steps (§6)

```
