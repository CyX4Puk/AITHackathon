# Продуктовые материалы — финальная версия

**Кейс:** агент и MCP-сервер для проверки контрагента в бизнесе  
**Дедлайн сдачи:** 04.09.2026 10:00  
**Статус:** текущая продуктовая проработка на основе `context_pack.md` и постановки кейса

---

## 1. Кто пользователь и какую проблему решает продукт

**Пользователь MVP:** предприниматель малого бизнеса — клиент банка (юридическое лицо), который перед сделкой или началом сотрудничества оценивает потенциальных контрагентов.

**Проблема:** пользователь получает отчёт по одному контрагенту за раз и самостоятельно изучает всё больше информации по мере расширения состава контрагентов. Типичная задача — выбрать из нескольких кандидатов, но инструмент заточен на поштучную проверку. Растёт время на анализ, ухудшается удобство при росте числа контрагентов, повышается риск пропустить значимый сигнал, снижается ценность и retention продукта «Проверка контрагента».

**Job (AJTBD):** перед сделкой быстро понять, с кем безопасно работать, где красные флаги и что проверить дополнительно — чтобы снизить риск плохой сделки и не читать длинные отчёты по каждому контрагенту отдельно.

## 2. Продуктовая гипотеза и ценностное предложение

### Гипотеза
Если в одной сессии показать сравнение контрагентов, сводку по рискам с фактами, перечень различий и рекомендации, что проверить, пользователь быстрее выберет приоритетного кандидата, чем при ручном просмотре отчётов. Уточняющие вопросы в чате для тех, кто хочет докопаться глубже; ответы только по данным отчёта.

**Самое рискованное предположение (RAT):** пользователь будет доверять обоснованному сравнительному виду и risk summary достаточно, чтобы принять решение по сделке без перечитывания полных отчётов. Без доверия агент останется декоративным интерфейсом над тем же ручным процессом.

### Ценностное предложение
Объяснимый ИИ-анализ поверх данных банка: сравнение контрагентов в сессии, структурированная сводка фактов по каждому, ответы строго по данным отчёта со ссылкой на поля и рекомендация следующего шага — без собственного скоринга, субъективного ранжирования сигналов и категоричных вердиктов.

**Отличие от аналогов:** не внешний сервис проверки компаний, а ИИ-помощник внутри банковского продукта: объясняет оценку риска и факты из данных банка, показывает различия между кандидатами и подсказывает, что проверить — без собственного скоринга и без вердикта за пользователя.

## 3. Границы MVP и основной пользовательский сценарий

### Входит в MVP
| Компонент | Зачем пользователю |
|---|---|
| Поиск по ИНН в CSV/JSON-выгрузке | Добавление контрагентов в сессию без банковских API |
| Сравнение 2–5 контрагентов в сессии | Выбрать, с кем работать в первую очередь, в одном месте |
| Карточка контрагента + `risk_level` + финансы + юр. события | Контекст по каждому кандидату; доступна по клику |
| Risk summary по каждому (4–5 фактов: оценка банка, финансы, юр. события, реестры ФНС; явные пробелы) | Сократить время до первого вывода |
| Перечень различий без ранжирования «лучше/хуже» | Обоснование собственного выбора, не вердикт агента |
| Grounded Q&A со ссылками на поля | Уточнения без галлюцинаций |
| Рекомендация следующего шага | Направить действие, оставив решение пользователю |
| Память в пределах сессии | Диалог без потери контекста |

### Не входит в MVP
Собственная модель риска; субъективное ранжирование сигналов по важности; поиск по отрасли/региону/названию; анализ рисков связанных компаний; интеграции с банковскими и внешними API; большая база карточек; ролевая модель; долгосрочная память и мониторинг.

### Основной сценарий (happy path)
1. Пользователь вводит ИНН и добавляет 2–5 компаний в сессию.
2. Видит сравнительный вид по `risk_level`, финансам, юр. событиям и полноте данных; risk summary по каждому с пометками «недостаточно данных».
3. Получает перечень различий и рекомендации, что проверить до сделки по каждому кандидату — без ранжирования «лучше/хуже».
4. Задаёт уточняющие вопросы в чате → ответы только по данным отчёта со ссылками на поля.
5. Принимает решение самостоятельно: с кем начать и что проверить по каждому.

## 4. Предварительные критерии успеха

Экспертная оценка (эталонного датасета нет). Решение успешно, если агент:

| Критерий | Как проверяем |
|---|---|
| Не выдумывает факты | Ответы опираются только на входные данные |
| Явно говорит о пробелах | Отсутствие данных ≠ отсутствие риска |
| Не даёт вердикт «не работать» | Только рекомендация следующего шага |
| Ускоряет вывод | Время до обоснованного решения меньше, чем у полного отчёта |
| Доверие через доказательства | Пользователь называет 2–3 факта из summary / сравнения |
| Сравнение работает | Пользователь выбирает кандидата и называет ≥2 различия; компанию с пропусками не считает «безопасной» |

Дополнительный плюс: удобный веб-интерфейс (сравнение + карточка + summary + чат; виджеты — по возможности).

## 5. Допущения, риски и план проверки гипотезы до финала

### Ключевые допущения
1. Главная ценность — не чат сам по себе, а risk summary с основаниями; при нескольких контрагентах — summary плюс сравнение в одной сессии.
2. Доверие растёт, если есть риск-метки, факты и ссылки на поля профиля.
3. Фиксированная структура фактов — оценка риска банка, финансы, юридические события, реестры ФНС и недостающие данные, упрощает анализ без субъективного определения важности сигналов.
4. Сравнение по единому набору критериев закрывает боль «десять отчётов подряд».
5. Перечень различий с рекомендацией по каждому воспринимается как обоснование выбора, а не как вердикт агента.
6. Для стабильных ответов LLM нужен подготовленный срез полей из JSON-отчёта и детерминированные правила — см. `profile_fields.md` и `signal_rules.md`.

### Риски
| Риск | Влияние | Митигация |
|---|---|---|
| Нет доверия к summary / сравнению (RAT) | Агент не меняет поведение пользователя | Факты и ссылки на поля; карточка по клику; тест без полного отчёта |
| Галлюцинации LLM | Провал критерия кейса | Grounding, guardrails, запрет домыслов |
| «Скажи, кто лучше» вместо различий | Пользователь ждёт вердикт | Формат ответа: различия + что проверить, без ранжирования «лучше/хуже» |
| Неполные данные в выгрузке | Ложное ощущение безопасности | Явный статус «оценка невозможна» |
| Перегруз интерфейса | Пользователь снова читает «всё подряд» | Сначала сравнение и summary, детали компании — по запросу |

### План проверки RAT до финала

**Подготовка:** выбрать 3 компании с разным `risk_level`, минимум одна с неполными данными; зафиксировать ожидаемые факты в summary и сравнении. Полный отчёт (исходная выгрузка / раздел данных банка) не показывать до завершения задания; карточка контрагента доступна по клику.

**Задание — несколько контрагентов в одной сессии:** показать 3 компании — сравнительный вид, risk summary по каждому, перечень различий с рекомендациями без полных отчётов и без ранжирования «лучше/хуже». Вопрос: «С кем из них вы начнёте работу и почему? Что проверите до сделки по каждому?»

**Метрики:** время до вывода; число уточняющих вопросов; ссылки на факты в ответах; субъективное доверие; приоритетный кандидат и ≥2 различия; реакция на компанию с пропусками; запрос вердикта «кто лучше»; добровольное открытие полных отчётов.

**Критерий успеха:** большинство участников (>50%) выбирают приоритетного кандидата, называют ≥2 различия, не трактуют компанию с пропусками как безопасную, принимают решение без запроса полных отчётов и опираются на факты из summary.

## 7. Связь продуктовых решений с технической реализацией

| Продуктовое решение | Техническое следствие |
|---|---|
| Данные только из отчёта / выгрузки | Моковая БД на CSV/JSON; без банковских API в демо |
| Не строить свою модель риска | `risk_level` — входной факт; агент объясняет, не пересчитывает |
| Сравнение в одной сессии | Единая схема критериев, session memory на 2–5 компаний, перечень различий |
| Risk summary с доказательствами | Pipeline: извлечение полей по `profile_fields.md` → `signal_rules.md` → краткий вывод с ссылками на поля |
| Grounded Q&A | Orchestration с ограничением контекста извлечёнными фактами; guardrails против галлюцинаций |
| Рекомендация без вердикта | Шаблон ответа: факты → риски/пробелы → следующий шаг из фиксированной таблицы «сигнал → действие»; без ранжирования «лучше/хуже» |
| Смешанный UX | Сравнение + карточка по клику + summary + чат (+ виджеты при наличии данных) |
| MCP опционален | Отдельный слой доступа к мок-базе — после ядра агента и UI |
| Веб-поиск — расширение | Явное отделение внешних находок от банковских данных; приоритет отчёта |

Итоговая продуктовая рамка для инженерии: **объяснимый агент поверх структурированного профиля** с сравнением контрагентов в сессии, а не чат над сырым текстом отчёта и не новый скоринг.
