## 1. Аннотация

Мы делаем ИИ-агента поверх продукта банка «Проверка контрагента». Агент получает отчёты по компаниям из предоставленной выгрузки (100 отчётов в формате `GetFullReportResponse`), прогоняет их через детерминированный набор правил, собирает по каждой компании короткую сводку из 4–5 фактов со ссылками на поля отчёта, сравнивает 2–5 контрагентов в одной сессии по единому набору критериев и отвечает на уточняющие вопросы только по данным отчёта. Метка риска банка `risk_level` принимается как готовый вход и не пересчитывается. Агент не выносит вердикт «не работать», а рекомендует следующий шаг из фиксированной таблицы «сигнал → действие».

На момент сдачи готовы: продуктовая рамка (границы MVP, гипотезы, план проверки самого рискованного предположения), спецификация профиля контрагента и правил срабатывания сигналов, проверенных на всей выгрузке, системный промпт агента, каркас сервисов (LangChain-агент с MCP-клиентом, Gradio-чат, заглушка MCP-сервера, docker-compose с профилем vLLM). Движок правил, реальные MCP-инструменты над выгрузкой и интерфейс сравнения ещё не реализованы.

## 2. Проблематика

Клиент банка (юрлицо, чаще всего малый бизнес) проверяет контрагента по объёмному отчёту: реквизиты, финансы за несколько лет, исполнительные производства, арбитраж, проверки, реестры ФНС, репутационные факторы. Отчёт растёт по мере добавления данных, а проверки запускаются по одной. Если поступили предложения от нескольких компаний, каждую нужно открыть отдельно и самостоятельно сопоставить.

Цена боли выражена качественно: растёт время анализа, при нескольких кандидатах продукт становится неудобным, значимый сигнал легко пропустить. Кейсодатель на Q&A подтвердил, что целевая метрика продукта не факт сделки, а вовлечённость и возвращаемость клиента к проверкам. Он же отметил, что пользователи чаще всего не читают 10–12 разделов отчёта, а смотрят на итоговую метку риска.

## 3. Актуальная постановка задачи

Постановка уточнена по итогам Q&A с кейсодателем (Денис Анастасьев) и зафиксирована в `reqs/context_pack.md`.

Ядро MVP:

- поиск контрагента по ИНН в выгрузке (CSV/JSON моделирует внутреннюю предагрегированную базу банка; доступа к банковским API нет);
- карточка контрагента: базовый профиль, `risk_level` и `zskRiskLevel`, финансы за 3 года, юридические события, реестры ФНС;
- risk summary из 4–5 фактов по фиксированной структуре (оценка банка, финансы, юридические события, реестры ФНС, дополнительный факт) с явным перечнем критериев, по которым оценка невозможна;
- grounded Q&A: ответы только по данным отчёта, каждый факт со ссылкой на поле вида `[finReports[year=2024].common.proceeds]`;
- сравнение 2–5 контрагентов в сессии по единому набору строк: оценка банка, финансы, юридические события, реестры ФНС, полнота данных;
- рекомендация следующего шага без вердикта; действия берутся из таблицы «сигнал → шаг»;
- память в пределах сессии.

Правила, подтверждённые кейсодателем: `risk_level` не пересчитываем и не оспариваем; отсутствие данных не равно отсутствию риска; универсального набора «главных» сигналов нет, поэтому агент не ранжирует сигналы по важности, а показывает факты в фиксированной структуре; веб-поиск допустим как дополнение, при противоречии приоритет у данных отчёта.

Второй эшелон (если успеем): контекст сделки (цель и сумма, сопоставление суммы с выручкой), пресеты вопросов, связанные компании, веб-поиск, экспорт сводки. Вне scope: собственная модель риска, поиск по отрасли/региону, интеграции с банковскими и внешними API, ролевая модель, долгосрочная память.

## 4. Выбранное техническое решение

Ключевое архитектурное решение: LLM не получает сырой отчёт и не решает, что важно. Между данными и моделью стоит детерминированный слой правил.

```
JSON report (Mongo Extended JSON)
  → нормализация типов ($date, $numberLong, строки-суммы, кириллица в кодах)
  → извлечение полей по блокам A–G (profile_fields.md)
  → применение правил IF/THEN (signal_rules.md §3)
  → signals / gaps / summary_slots / next_steps (signal_rules.md §6)
  → LLM: текст сводки, перечень различий, Q&A по извлечённым фактам
```

Это даёт три свойства, которых требует кейс: проверяемость (каждый факт в сводке имеет ID правила и поле-источник), воспроизводимость (одинаковые отчёты дают одинаковые слоты) и контроль галлюцинаций (модель формулирует текст по готовым сигналам и выбирает действие из фиксированной таблицы, а не придумывает своё).

Стек (ветка `feat/base-scaffold`):

| Компонент | Реализация |
|---|---|
| Агент | LangChain `create_agent` + LangGraph `InMemorySaver` (память сессии по `thread_id`) |
| Инструменты | `langchain-mcp-adapters` `MultiServerMCPClient`, транспорт streamable HTTP |
| MCP-сервер | Python `mcp` (`MCPServer`), uvicorn, порт 3010, том `./data` монтируется в контейнер |
| LLM | Профили в `llm_config.json`: локальный vLLM (`Qwen3.6-27B-AWQ-INT4`, порт 3040) или API `qwen3.5-27b`; переключение через `ACTIVE_LLM_PROFILE` |
| Инференс | Docker-профиль `vllm` с `--enable-auto-tool-choice --tool-call-parser qwen3_xml`, prefix caching |
| UI | Gradio `ChatInterface`, порт 7860 |
| Общее | `shared/utils/logger.py`, `docker-compose.yml` |

Роль агента в промпте: «секретарь»-оркестратор, который сам не хранит данных о компаниях и получает их только через MCP-инструменты. Промпт (`services/prompts/system_prompt_agent.md`) содержит запрет на галлюцинации, обязательный формат ссылок на поля, скрытую самопроверку перед ответом (подкреплено ли каждое утверждение полем; не выдано ли отсутствие данных за отсутствие риска; не вынесен ли вердикт), структуру ответа по одному контрагенту и режим сравнения без числового рейтинга.

## 6. Предварительные результаты

Код движка правил ещё не написан, но правила прогнаны на выгрузке аналитически (Python-скрипты над JSON), и по результатам исправлены сами правила и продуктовые решения.

Профиль выгрузки (100 отчётов): `riskLevel` LOW 78, MEDIUM 15, HIGH 4, UNKNOWN 3; `zskRiskLevel` GREEN 81, YELLOW 18, RED 1; все компании со статусом CURRENT; 25 записей из 100 — ИП (ИНН 12 знаков) без финотчётности и учредителей; `finReports` отсутствует у 33 компаний, `inspections` у 70.

Что дал прогон правил:

- Сборка сводки работает на всех 100 отчётах: 41 сводка из 4 фактов, 59 из 5. Слоты 1–4 заполняются всегда, потому что у каждого есть gap- или info-fallback.
- Распределение по слоту «финансы»: `FIN_MISSING` 33, `FIN_PROCEEDS_UP` 31, `FIN_PROCEEDS_DOWN` 11, `FIN_TREND_INSUFFICIENT` 8, `FIN_EMPTY` 5. По слоту «юридические события»: `EP_NONE` 38, `EP_HISTORY_ONLY` 23, `EP_ACTIVE` 18, `ARB_DEFENDANT_OPEN` 8. По реестрам ФНС: `REG_CLEAN` 76, `REG_MASS_ADDRESS` 13, `REG_FNS_BLOCKING` 6.
- Правило `LICENSE_OKVED_GAP` («нет лицензии под лицензируемый ОКВЭД») убрано из MVP: список ОКВЭД 41/42/43/49 давал 29 ложных срабатываний из 100, потому что строительство лицензий не требует. Вернём после согласования списка с кейсодателем.
- Правило «смена учредителя/руководителя» без исключения дат, совпадающих с регистрацией, дублировало `YOUNG_COMPANY` ложным сигналом у всех молодых компаний. После исключения (окно 30 дней от `registrationDate`) осталось 24 реальные смены руководителя за 2025–2026.
- Найдены ловушки данных, которые попали в раздел нормализации: `finReports` не отсортирован по годам у 65 из 67 компаний; ключ `profit` есть только в 79 из 194 годовых записей; суммы исполнительных производств у ИП — строки, у 770 из 3873 записей `null`; позитивный репутационный код `аrbitrationDefendant` содержит кириллическую «а»; поле активности учредителя в спецификации называется `isActive`, в выгрузке `active`.

Продуктовый результат: Q&A с кейсодателем снял четыре ключевые неопределённости (мок-данные вместо API, `risk_level` как вход, МСП как базовый пользователь, память только в сессии) и сместил фокус MVP с «чата над отчётом» на сравнение нескольких контрагентов в одной сессии.

## 7. Ограничения

- Данных банка нет: выгрузка из 100 отчётов моделирует внутреннюю базу; онлайн-запросов к источникам в демо не будет.
- `risk_level` принимается как есть; агент объясняет метку через факты отчёта, но не может объяснить формулу её расчёта (она закрыта).
- В выгрузке нет отчётов по связанным компаниям, поэтому их риск-профиль показать нельзя, только реквизиты связи.
- Для ИП оценка финансов по отчёту невозможна в принципе (ИП не публикует бухгалтерскую отчётность); сводка это явно сообщает.
- Отсутствие раздела в отчёте трактуется как пробел данных, а не как «событий не найдено». Это консервативное допущение и может занижать «полноту данных» в сравнении.
- Инференс Qwen 27B локально требует GPU; для демо с Mac предусмотрен профиль с внешним API.
- Качество оценивается экспертно; эталонного датасета для автоматической валидации нет.

## 8. Открытые вопросы

Кейсодателю:

- Можно ли показывать клиенту `zskRiskLevel` YELLOW/RED как есть? По спецификации интерфейс банка выводит клиенту Green/grey/grey.
- Какие ОКВЭД считать лицензируемыми для правила «нет лицензии под основной вид деятельности»?
- `baseInfo.riskLevel = UNKNOWN` у 3 компаний не описан в спецификации. Трактуем как пробел данных, верно ли?
- Отсутствие раздела (`inspections` нет у 70 компаний, `finReports` у 33) — «данных нет» или «событий не найдено»?
- Нужны ли для ИП иные критерии оценки, кроме юридических событий и реестров?
- Какие типовые вопросы предприниматель задаёт чаще всего после ввода ИНН (для пресетов и тестов)?

Внутри команды:

- Где живёт движок правил: внутри MCP-сервера (инструмент возвращает готовые `signals`) или в агенте между инструментом и LLM. Рабочий вариант: в MCP-сервере, чтобы LLM видела только структурированный результат.
- Интерфейс сравнения: остаёмся в Gradio (Blocks с таблицей и карточкой рядом с чатом) или отдельный фронт. Для сдачи 07.09 выбираем Gradio.
- Как проверять грандинг ответов автоматически: сверка ссылок `[поле]` в ответе с реально полученными от инструмента полями.
