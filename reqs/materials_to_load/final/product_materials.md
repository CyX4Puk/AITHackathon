## 1. Пользователь и проблема

**Пользователь:** предприниматель малого бизнеса — клиент банка, который перед сделкой или выбором поставщика оценивает контрагентов.

**Проблема:** банк выдаёт объёмный отчёт по одной компании. Разделов много, проверки идут поштучно. Если кандидатов несколько, пользователь листает профили по очереди и держит различия в голове. Растёт время, падает удобство, легко пропустить рискованный фактор.

Кейсодатель подтвердил: метрика продукта — не факт сделки, а возврат к проверкам. Пользователи чаще смотрят итоговую метку риска, а не 10–12 разделов.

**Job:** перед сделкой быстро понять, где красные флаги и что проверить, не читая полный отчёт по каждому кандидату отдельно.

## 2. Гипотеза и ценность

**Гипотеза.** Если в одной сессии дать сводку по фактам, сравнение по одним критериям и возможность открыть источник из чата, предприниматель быстрее выберет кандидата, чем при ручном просмотре отчётов. Банк получает более полезный сервис и повод вернуться к проверке.

**Самое рискованное предположение (RAT):** пользователю хватит сводки и сравнения, чтобы принять решение без перечитывания полных отчётов. Без доверия агент останется оболочкой над тем же ручным процессом. Это проверяем на пилоте, не на хакатоне.

**Ценность.**

| Кому | Что получает |
| --- | --- |
| Предприниматель | Меньше ручного сравнения: сводка, различия, что проверить |
| Банк | Отчёт становится диалогом; выше шанс повторной проверки |

**Отличие от аналогов.** Не отдельный Контур / СПАРК, а помощник внутри банковского продукта: объясняет факты из данных банка, не строит свой скоринг и не говорит «не работать».

Три свойства продукта, которые показываем в демо:

| Особенность | Что получает пользователь |
| --- | --- |
| Подтверждение фактами | Вывод связан с данными профиля, источник открывается из чата |
| Подробное сравнение | Несколько кандидатов в одной сессии по одним направлениям |
| Подписка на обновления | Можно следить за выбранными компаниями, не проверяя заново вручную |

## 3. Что входит в прототип и сценарий

### Есть в демо

| Компонент | Зачем |
| --- | --- |
| Поиск по ИНН в выгрузке 100 отчётов | Добавить компанию без банковского API |
| Сводка по пяти направлениям | Оценка банка, финансы, юридические события, реестры ФНС, полнота данных |
| Сравнение до 10 компаний в сессии | Одни критерии, без «лучше / хуже» |
| Карточка и переход от факта к источнику | Проверить вывод, не доверяя модели вслепую |
| Вопросы в чате | Уточнения по данным отчёта |
| Контекст сделки | Цель и сумма в той же сессии |
| Подписка на обновления | Задел на мониторинг после проверки |
| Память сессии | Диалог не сбрасывается между репликами |

Метка `risk_level` — вход банка, не наш пересчёт. Агент даёт рекомендации, не вердикт.

### Не входит в демо

Собственная модель риска; живые API; риски связанных компаний; поиск по отрасли; долгосрочная память; полный детерминированный движок из 40+ правил спецификации (он описан в `signal_rules.md` и использован как контракт сводки, в рантайме — компактная проекция отчёта).

### Сценарий

1. Пользователь описывает задачу или вводит ИНН (можно сразу несколько и контекст сделки).
2. Видит сводку по компании: факты, пробелы, что проверить.
3. Сравнивает кандидатов в панели по тем же пяти направлениям.
4. Кликает факт — открывается блок профиля-источника.
5. Задаёт вопрос в чате. Решение, с кем работать, принимает сам.

## 4. Критерии успеха

На хакатоне проверяли корректность ответов на данных: **190/200** корректных, 9 пустых, 1 галлюцинация. Эталонного пользовательского датасета нет.

Продуктовый успех — на пилоте, не в демо:

| Критерий | Как смотрим |
| --- | --- |
| Не выдумывает факты | Ответ опирается на отчёт; источник можно открыть |
| Пробелы видны | Компанию без данных не считают «безопасной» |
| Нет вердикта | Нет «не работайте»; есть что проверить |
| Сравнение работает | Пользователь называет различия между кандидатами |
| Быстрее ручного отчёта | Время до решения на пилоте |
| Доверие | Решение без обязательного чтения полного отчёта |

## 5. Допущения, риски, проверка

**Допущения.** Ценность — сводка и сравнение, не чат ради чата. Доверие растёт, если факт можно открыть в профиле. Одинаковые направления на всех кандидатах закрывают боль «десять отчётов подряд». Модель пишет текст по срезу отчёта, а не по сырому JSON.

**Риски**

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Нет доверия к сводке (RAT) | Пользователь снова читает полный отчёт | Клик из чата в источник; пилот |
| Галлюцинации | Провал кейса | Срез сигналов, JSON-схема, проверка id/путей; 1 ошибка в прогоне из 200 |
| Ждут «кто лучше» | Конфликт с правилом кейса | Различия и шаги, без рейтинга |
| Неполные данные | Ложное спокойствие | Явный пробел в сводке |
| Узкая проверка текста модели | Цифра в фразе может не совпасть с отчётом | Не обещаем полную сверку каждого числа; ловим служебные поля и утечки имён |

**Пилот (вместо проверки RAT на хакатоне):** 2–4 недели, 10–15 пользователей МСП. Сценарий — несколько контрагентов и контекст сделки. Метрики: время до решения, число галлюцинаций.

Дальше: связанные компании → сопровождение договора и банковские услуги → подбор поставщиков. Остальные идеи — `reqs/ideas.md`, в питч не выносили.

## 7. Продукт → техника

| Продуктовое решение | Как сделано в прототипе |
| --- | --- |
| Данные только из отчёта | MCP `get_companies_info_by_inn` по выгрузке JSON |
| Не свой скоринг | `risk_level` — входной факт |
| Сравнение в сессии | До 10 компаний, одни направления, без рейтинга |
| Вывод можно проверить | Факт в чате открывает блок профиля; технические пути скрыты |
| Модель не ищет отчёт сама | Бэкенд решает, звать ли инструмент, затем Qwen формулирует JSON |
| Рекомендация без вердикта | Сводка и «что проверить», решение за пользователем |
| Смешанный UX | Launcher → чат + панель (карточка, сравнение, графики) |

Для защиты: **объяснимый помощник поверх данных банка**, а не новый скоринг и не чат над сырым текстом.
