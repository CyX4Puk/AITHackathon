## 1. Аннотация

Внутрибанковский ИИ-помощник для предпринимателя МСП. По ИНН агент запрашивает отчёт о компании, собирает короткую сводку по пяти направлениям и позволяет сравнить до 10 кандидатов в одной сессии. Каждый вывод можно открыть в профиле и проверить. Решение о сделке остаётся за пользователем.

Прототип готов к демо. Чат отдаёт запрос бэкенду. Бэкенд сам решает, нужны ли данные, вызывает MCP-инструмент, получает отчёт по ИНН, разбирает его и просит Qwen 3.8 27B сформулировать структурированный ответ. Интерфейс рисует сводку, сравнение и карточку компании.

Метка риска банка принимается как входной факт и не пересчитывается. Агент не даёт категоричных указаний, только рекомендации.

---

## 2. Проблема

Клиент банка проверяет контрагента по объёмному отчёту: реквизиты, финансы, исполнительные производства, арбитраж, проверки, реестры ФНС. Отчёт растёт, проверки идут по одной компании. Если кандидатов несколько, пользователь листает профили по очереди и держит различия в голове.

Кейсодатель подтвердил: целевая метрика продукта — не факт сделки, а возврат к проверкам. Пользователи чаще смотрят итоговую метку риска, а не 10–12 разделов.

Для предпринимателя продукт сокращает ручное сравнение. Для банка — делает отчёт полезнее и даёт повод вернуться в сервис.

---

## 3. Постановка

Постановка зафиксирована после Q&A с кейсодателем (Денис Анастасьев) в `reqs/context_pack.md`.

**Пользователь:** предприниматель МСП, клиент банка, перед сделкой или выбором поставщика.

**Что делает агент:** компактный профиль → сводка фактов → сравнение → что проверить → уточнение в чате.

**Пять направлений оценки:** оценка банка, финансы, юридические события, реестры ФНС, полнота данных.

**Правила кейса, которые соблюдаем:**

- поиск по ИНН в выгрузке (CSV/JSON моделирует внутреннюю базу; банковских API нет);
- `risk_level` и `zskRiskLevel` не пересчитываем;
- отсутствие данных ≠ отсутствие риска;
- ответы только по данным отчёта;
- сравнение без рейтинга «лучше / хуже» и без вердикта;
- память в пределах сессии.

**В прототипе сверх исходного ядра:** до 10 компаний в сессии, контекст сделки, подписка на обновления в интерфейсе.

**Вне scope демо:** собственная модель риска, живые API банка, риски связанных компаний, поиск по отрасли, долгосрочная память.

## 4. Техническое решение

Бэкенд-агент не хранит карточки компаний. Данные приходят отдельным инструментом. Модель формулирует ответ, а не ищет отчёт.

```
Чат (запрос пользователя)
    → бэкенд-агент (сессия, решение вызвать инструмент, разбор отчёта)
        → MCP-сервер: отчёт по ИНН
        → Qwen 3.8 27B: структурированный ответ
    → чат и панель сравнения
```

**Поток данных.** MCP-инструмент `get_companies_info_by_inn` находит компанию в `data/contractors_audit.snapshot.json` и отдаёт сырой отчёт. Агент проецирует отчёт в компактный набор сигналов (оценка банка, выручка, исполнительные производства, арбитраж, реестры ФНС, статус). Этот срез уходит в модель. Модель возвращает JSON по схеме. Код проверяет, что служебные id сигналов и пути полей есть во входном срезе, и ловит утечки технических имён в текст. Несовпадение не вырезает ответ из чата: валидация служебная, а не гарантия каждой цифры в русской фразе.

**Стек**

| Слой | Реализация |
| --- | --- |
| Интерфейс | Чат + панель «Подробности»: сводка, карточка, матрица сравнения. Макет — `reqs/ui/mockup.html` |
| Агент | Бэкенд-оркестратор, память сессии, вызов MCP, structured output |
| Инструменты | MCP, streamable HTTP |
| Данные | Выгрузка 100 отчётов `GetFullReportResponse` |
| LLM | Qwen 3.8 27B |
| Правила | Спецификация `reqs/signal_rules.md` (40+ условий). В прототипе — компактная проекция отчёта в сигналы на стороне агента, не полный IF/THEN-движок |

Так данные остаются отделены от языковой модели: MCP отдаёт отчёт, агент решает, что взять, модель пишет текст в фиксированной форме.

## 5. Что реализовано к защите

**Продукт и интерфейс**

- Пустая сессия: task-first launcher, ввод ИНН, контекста сделки или запроса на сравнение.
- Сводка по компании и переход от факта в чате к блоку-источнику в профиле.
- Сравнение отобранных компаний по одним направлениям, до 10 в сессии.
- Подписка на обновления по выбранной компании (в макете).
- Демо-сценарий: несколько ИНН и контекст сделки в одном запросе.

**Данные и спецификации**

- Выгрузка 100 отчётов: JSON и CSV.
- `profile_fields.md` — блоки карточки и зоны отображения.
- `signal_rules.md` — детерминированные правила, слоты сводки, таблица «сигнал → шаг»; правила прогнаны аналитически на всей выгрузке.
- Системный промпт: факты только из отчёта, без вердикта, без технических путей в тексте пользователю.

**Агент и MCP**

- Инструмент поиска по ИНН, передача отчёта агенту, сборка ответа для фронта.
- Structured output в JSON-схеме, чтобы интерфейс рисовал карточки, а не свободный текст.
- Прогон ответов на данных: **190/200** корректных, 9 пустых (скорее параллельные запросы), 1 галлюцинация. На слайде открытия это **95%** корректных ответов.

## 6. Ограничения

- Статичная выгрузка вместо живого API банка. Связи компаний в отчёте есть как реквизиты, риск связанных лиц по отдельным отчётам не проверяется.
- Формула `risk_level` закрыта: агент объясняет метку фактами отчёта, но не воспроизводит скоринг банка.
- Для ИП оценка финансов по бухгалтерской отчётности невозможна; сводка это говорит явно.
- Отсутствие раздела трактуется как пробел данных, не как «событий не было».
- Проверка содержания ответа узкая: сверяются id сигналов и пути полей, не каждое число в тексте. Для свободного вопроса (`qa`) карточки фактов пустые.
- Эффект на время решения и retention — гипотеза пилота, не измеренный результат хакатона.
