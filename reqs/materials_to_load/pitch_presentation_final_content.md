## Слайд 6. Техника

**Время:** 3:10–4:10 · заголовок слайда = вывод

### На слайде

**Агент не хранит данные — факты приходят из MCP-сервера, текст формулирует LLM**

**Архитектура (`main`)**

```
Веб-интерфейс (чат + панель)
        ↓
Агент-оркестратор (LangChain + память сессии)
        ↓ streamable HTTP
MCP-сервер verification_mcp_server (:3010)
  → JSON-выгрузка отчётов (data/)
  → нормализация → 40+ правил → signals / gaps / next_steps
        ↓
Qwen 3.8 27B (structured JSON) → валидатор G3/G4 → ответ в UI
```

**Инструменты MCP** (контракт `functional_spec.md` §7)

| Инструмент | Назначение |
| --- | --- |
| `get_report` | Отчёт по ИНН |
| `list_reports` | Список доступных компаний |
| `analyze` | Сводка: сигналы, пробелы, профиль |
| `compare` | Матрица различий для 2–10 контрагентов |

**Стек**

| Слой | Реализация |
| --- | --- |
| UI | `web/index.html` — чат, панель, сравнение, графики |
| Агент | LangChain `create_agent` + LangGraph `InMemorySaver`; демо-HTTP — `web_agent.py` (`/chat`) |
| MCP-клиент | `langchain-mcp-adapters` · `MultiServerMCPClient` |
| MCP-сервер | FastMCP · uvicorn · Docker · том `./data` |
| Правила | `signal_rules.md` — детерминированный слой в MCP |
| LLM | Qwen 3.8 27B: LM Studio / vLLM (Docker) / API · `report_contract.py` (JSON Schema) |
| Данные | `contractors_audit.snapshot.json` — 100 отчётов, Mongo Extended JSON |

**Почему так**

- Агент-«секретарь» сам не хранит данные о компаниях, только вызывает MCP.
- LLM не видит сырой отчёт: в промпт попадают только `analyze` / `compare`.
- Одинаковые данные → одинаковые факты; модель отвечает за язык.
- Метка риска банка — входной факт, не пересчитываем.

**Метрики и проверки**

- 100/100 сводок в прогоне правил; 29 ложных срабатываний LICENSE убрано.
- **[N/N]** контрольных вопросов · **[X с]** медиана ответа · **[0]** выдуманных чисел в прогоне.

**Ограничения:** моковая выгрузка вместо API банка; формула `risk_level` закрыта; эффект на retention — гипотеза пилота.

**Вклад команды:** продукт, правила, контракт MCP (Илья) · агент, MCP, structured output (Алексей) · UI, данные, интеграция (Павел).

### Речь

«Архитектура трёх слоёв. Веб-интерфейс показывает чат и панель сравнения. Агент на LangChain не держит данные о компаниях — он ходит в MCP-сервер за отчётами, анализом и сравнением. На сервере лежит выгрузка из ста отчётов и детерминированный движок из сорока правил: он нормализует JSON, собирает сигналы и пробелы. Qwen получает только готовую структуру и возвращает текст в JSON Schema. Валидатор проверяет, что каждый факт был во входе. Так мы контролируем галлюцинации и можем воспроизвести любой ответ».

### Визуал

Схема из 5 блоков: UI → Агент → MCP-сервер (данные + правила) → LLM → Валидатор. Под схемой — таблица инструментов MCP, не список технологий.

### Примечание спикеру

Если спросят про демо: `web_agent.py` на `main` принимает уже посчитанные `analyze_results` и отвечает за язык модели; целевая схема — все вызовы `analyze` / `compare` через MCP, как в `docker-compose.yml` и `agent.py`.
