## Слайд 3. Ценность

**Время:** ~15–20 с внутри блока 0:30–1:00 (сразу после продукта, без отдельного длинного слайда)

### На слайде

**Предприниматель: решает проблему трудоёмкого сравнения компаний. Банк: повышает лояльность клиентов**

| Что меняется | Для кого | Эффект |
| --- | --- | --- |
| **Быстрее** | Предприниматель | Сводка и сравнение вместо изучения полных отчётов подряд |
| **Точнее** | Предприниматель | Единые критерии по всем кандидатам, отсутствует риск пропустить сигнал |
| **Понятнее** | Предприниматель | Различия и рекомендации для уточнений у контрагентов  |
| **Чаще возвращаются** | Банк | Продукт полезен при выборе контрагентов |


**Гипотеза пилота:** предприниматель сравнивает несколько контрагентов, быстрее и без ошибок выбирает, с кем сотрудничать.

### Речь

«Ценность — не в том, что агент решает за клиента. Он ускоряет путь к обоснованному действию: что проверить, у кого, и почему. Для банка это рост вовлечённости в продукт проверки. Эффект на retention пока гипотеза — проверим на пилоте с 10–15 пользователями».

### Визуал

Три колонки «процесс → пользователь → эффект». Отдельно пометка: измерено / гипотеза.

## Слайд 4. Ключевые особенности продукта

**Время:** 1:00–1:20

### На слайде

**ИИ объясняет отчёт, правила контролируют проверку, факты подтверждают вывод**

| Особенность | Что получает пользователь |
| --- | --- |
| **Диалог с ИИ** | Задаёт вопросы обычным языком и получает краткий ответ вместо поиска по разделам отчёта |
| **Движок правил** | 40+ детерминированных проверок находят рискованные факторы и пробелы в данных |
| **Подтверждение фактами** | Каждый вывод связан с конкретными данными профиля; источник можно открыть и проверить |
| **Сравнение компаний** | До 10 контрагентов оцениваются по одинаковым направлениям в одной сессии |

### Речь

«В продукте четыре ключевых элемента. ИИ даёт понятный диалоговый интерфейс. Детерминированные правила отвечают за проверку и не зависят от формулировок модели. Каждый вывод можно подтвердить конкретным фактом из профиля компании. А сравнение в одной сессии позволяет применить одинаковые критерии сразу к нескольким кандидатам».

### Визуал

Четыре связанные карточки: «Диалог» → «Правила» → «Факты» → «Сравнение». Центральный акцент — «вывод можно проверить».

### На слайде

**Три контрагента и контекст сделки — один сценарий, один следующий шаг**

**Сценарий:** поставка на 100 млн ₽.

1. `Проверь 9721159668, 1660266560 и 9714079997. Планируется поставка на 100 млн ₽.`
2. Сводка: оценка банка, факты, пробелы, «что проверить».

## Слайд 6. Техника

**Время:** 3:10–4:10 · заголовок слайда = вывод

### На слайде

**Агент через инструмент умеет получать данные, если решает что это необходимо. Инструменты находятся на MCP-сервере. Получив данные, агент их анализирует и передает в виде json-схемы, которая парсится на фронтенде**

**Архитектура**

```
Веб-интерфейс (чат + панель)
        ↓
Агент-оркестратор (LangChain + память сессии)
        ↓ streamable HTTP
MCP-сервер verification_mcp_server (:3010)
  → отчет в JSON-формате
  → Structured output
        ↓
Qwen 3.8 27B / Deepseek-V4-flash → валидатор с логикой правил → ответ в UI
```

**Инструмент MCP-cервера - get_companies_info_by_inn. Ищет и передает агенту данные по ИНН. Составляет матрицу для сравнения.**

**Метрики и проверки**

- 190/200 корректных ответов в прогоне на данных; 9 пустых ответов(вероятно, из-за параллельных запросов), одна реальная галлюцинацияя.

**Ограничения:** статичная выгрузка вместо живого API, без возможности проверить связи компаний; формула `risk_level` закрыта.

**Вклад команды:** продукт, правила, UI (Илья) · агент, MCP, интеграции с LLM (Алексей и Павел).

### Визуал

Схема из 5 блоков: UI → Агент → MCP-сервер (данные + правила) → LLM → Валидация JSON-схемы.

### Примечание спикеру

Если спросят про демо: агент на  принимает результат работы MCP-сервера и отвечает за формулировку и структуру данных.
